# CPU batch allocation measurements

Measured locally on 2026-10-20 (Asia/Shanghai); raw metadata uses UTC timestamps.
This stage measures pure and mixed batches and reduces temporary allocations in
observation and density-matrix reverse passes.

## Workloads and controls

The [entrypoint](../../benchmark/batch_execution.jl) uses four- and six-qubit,
two-layer Ry/Rz/CNOT circuits, with batch counts 1, 4, 16, and 64. Cases start
from a `BatchStateVector` or a genuinely mixed `BatchDensityMatrix`, with or
without fixed amplitude damping in each layer. Mixed inputs are
`0.8|psi><psi| + 0.2I/D`. All sizes use prefixes of one seeded batch. Each
layer and sample shares the same independent Ry/Rz parameters: 16/24 active
slots map to 8/12 values for four/six qubits. The observable is
`0.7 Z₁ + 0.3 X₁Xₙ`, with mean reduction.

Each case measures a general two-qubit gate, initial-state expectation, scalar
forward evaluation, complete explicit gradient, pullback preparation, and
application of an already prepared pullback. Noise cases also measure one
fixed amplitude-damping channel. The gate/channel microbenchmarks reset private
storage in BenchmarkTools setup, outside timing, and use one evaluation per
sample. Internal promotion, including pure-to-mixed allocation, stays inside
`apply!`. Objective operations include binding and their defensive copies.
Correctness references, construction, package loading, and compilation warmup
are outside the warmed trials. Explicit single-state loops check correctness;
these records do not time a batch-versus-loop comparison.

Measurements use Julia 1.13.1, Linux x86_64, AMD RYZEN AI MAX+ 395 with 32 logical
CPU threads, ComplexF64 states, Float64 parameters, seed 20261020, and one
OpenBLAS thread. Each before/after pair uses the same Julia thread count (one
or four), frozen scripts, and resolved BenchmarkTools environment. Trials run
sequentially in fresh processes without competing Julia test or benchmark jobs.
All formal records are warmed medians (`--steady-only`); neither Zygote nor
ChainRulesCore is loaded. No first-call latency claim follows from these trials.

## Changes selected by allocation profiling

The diagnostic [profile script](cpu-batch-2026-10-20/allocation_profile.jl)
warms a mixed unitary objective and records the minimum of three `@allocated`
calls. A full `Profile.Allocs` pass attributes a six-qubit, B=16 pullback's
largest allocations to the two derivative vectors in `_density_gate_gradients`:
25,187,328 bytes each. Repeated allocation of these dense payloads accounts for
about 50.4 MB of the 59.7 MB pullback allocation.

Density reverse passes now reuse two typed vectors within one invocation,
including nested circuits. Both are refilled for every derivative, and a change
in scalar domain or size replaces the pair. Channel checkpoints retain their
existing reconstruction rules, including singular channels. For the profiled
B=16 case, total vector allocation at this site becomes 2,098,944 bytes.

Short one-, two-, and three-qubit density observables now contract read-only
sample views using one promoted local matrix per term or group. They avoid
whole-sample copies and retain observable/state promotion and promoted trace
accumulation. Longer observables and gate/channel execution keep existing paths.

A prepared density-batch expectation pullback retains a private adjoint
observable and shape information rather than a copied state. Each invocation
creates one private identity and computes the fully seeded operator action.
Consecutive equal seeds of the same concrete type reuse that action across
samples. Applying the seed before operator products and sums retains the old
precision and underflow behavior, including seeds in a wider domain. Different
seeds remain valid and need a new action. No mutable numerical workspace is
retained across pullback calls.

Diagnostic allocated bytes for the six-qubit, B=16 mixed unitary objective:

| Operation | Before | After | Saved |
| --- | ---: | ---: | ---: |
| Initial expectation | 1,073,760 | 2,208 | 1,071,552 |
| Forward evaluation | 2,524,168 | 1,452,616 | 1,071,552 |

| Pullback application | 59,667,152 | 8,099,920 | 51,567,232 |
| Complete gradient | 64,526,504 | 10,841,184 | 53,685,320 |

The profiler's gate/channel diagnostics include the input copy, whereas the
formal gate/channel trials exclude it. Those microbenchmark byte counts should
not be compared across these two methods. The profile is allocation evidence,
not an elapsed-time trial.

## Matched warmed results

Six qubits, B=16, one Julia thread; allocated bytes per complete gradient and
per call to an already prepared pullback:

| Case | Gradient before → after | Reduction | Pullback before → after | Reduction |
| --- | ---: | ---: | ---: | ---: |
| Pure unitary | 2,522,456 → 2,522,456 | 0.00% | 2,099,280 → 2,099,280 | 0.00% |
| Mixed unitary | 64,526,424 → 10,841,104 | 83.20% | 59,667,152 → 8,099,920 | 86.42% |
| Pure fixed noise | 64,080,032 → 35,751,016 | 44.21% | 47,129,936 → 20,918,992 | 55.61% |
| Mixed fixed noise | 92,313,840 → 38,791,288 | 57.98% | 73,317,968 → 21,913,552 | 70.11% |

For the same mixed unitary case, preparation allocates 2,740,832 rather than
4,858,936 bytes (43.59% less). Initial mixed expectation allocates 2,208 rather
than 1,073,760 bytes. Small differences from the diagnostic table arise from the
different caller/closure contexts; comparisons within each method use identical
before/after workloads.

The four matched pairs of 104-row tables cover 416 comparisons. Across both
register sizes, both thread counts, and all four batch sizes, the gradient
allocation reductions span:

| Case | Complete gradient reduction | Prepared pullback application reduction |
| --- | ---: | ---: |
| Mixed unitary | 28.17–83.71% | 55.76–86.61% |
| Pure fixed noise | 14.11–44.54% | 30.31–55.84% |
| Mixed fixed noise | 23.51–58.25% | 46.16–70.26% |

All 176 selected controls (gate/channel microbenchmarks and pure unitary
operations) retain exactly the same allocated bytes and allocation counts.
Their elapsed before/after ratios nevertheless range from 0.72 to 1.30. Timing
results therefore describe these local trials rather than a general throughput
or thread-scaling guarantee. The slowest baseline B=64 operation has only six
samples; raw sample counts should accompany any timing interpretation.

An additional B=16, six-qubit, one-thread confirmation pair uses a two-second
trial budget and constructs only 16 seeded samples. Subsequent RNG draws differ
from the four-size workload, while the confirmation's before/after inputs match.
All 26 corresponding operations reproduce the main B=16 pair's allocated bytes and allocation counts
exactly, for both implementations. Its 52 raw rows bring the retained total to
884 summaries (442 matched pairs).

Dense storage and channel checkpoints still scale with the state and batch.
Long observables and distinct weighted seeds retain additional work outside the
optimized short-contraction and consecutive-equal-seed paths.

## Reproduction and retained records

The [artifact directory](cpu-batch-2026-10-20/) retains every formal TSV and
metadata file, the resolved benchmark Project/Manifest, frozen scripts,
production patch, diagnostic profile, source provenance, and comparisons.
Individual BenchmarkTools sample arrays were not serialized; TSV files contain
median summaries, sample counts, allocated bytes and allocation counts. Trial
budgets can end early at BenchmarkTools' 10,000-sample cap.

For reproduction, create two isolated copies of baseline `cd127e6`. Copy the
retained `Project.toml`, `Manifest.toml`, `batch_execution.jl`, and
`repeated_evaluation.jl` into each copy's `benchmark/` directory. Apply
`optimized-source.patch` only in the optimized copy, using
`git apply --unidiff-zero PATH/optimized-source.patch` (the retained patch omits
context lines). The saved Manifest uses
`MOSS` at relative path `..`, so each environment loads its own source tree.
Instantiate the environment with Julia 1.13.1 before measuring, preserving the
resolved versions. From each copy, run these commands sequentially, once for
each `N=4/6` and `T=1/4`, selecting the corresponding output filename:

```bash
julia --project=benchmark --threads=T benchmark/batch_execution.jl --steady-only --qubits N --depth 2 --batches 1,4,16,64 --seconds 1 --output /tmp/moss-batch-PHASE-nN-tT.tsv
```

The uppercase values above are placeholders. For the additional independent
confirmation pair, use six qubits, one Julia thread, `--batches 16`, and
`--seconds 2`. Selecting only B=16 consumes a different amount of random input
than the four-size workload, so it is a separate paired confirmation with
identical before/after inputs, rather than a literal repeat of its parameters.
The baseline confirmation uses an archive without `.git`; its recorded source
hashes and retained baseline provenance pin it to `cd127e6`.

Run the saved auditor with Python 3.11 or later against an optimized Git
checkout and the retained data to verify source hashes, control equality, and
row-by-row comparisons. Baseline `cd127e6` must be reachable in that checkout's
history; the auditor reconstructs its source using `git show`. Substitute
paths for `ARTIFACT_DIR` and `OPTIMIZED_CHECKOUT`:

```bash
python3 ARTIFACT_DIR/audit_records.py --root OPTIMIZED_CHECKOUT --data-dir ARTIFACT_DIR --repeat-before ARTIFACT_DIR/moss-batch-before-n6-t1-confirmation.tsv --repeat-after ARTIFACT_DIR/moss-batch-after-n6-t1-confirmation.tsv --output-json /tmp/moss-cpu-batch-audit.json
```

The optimized checkout must contain the saved benchmark Manifest. `SHA256SUMS`
checks the retained artifacts. See the
[benchmark guide](../../benchmark/README.md#pure-and-mixed-batch-execution)
for operation definitions, core/optional-AD smoke checks, and environment setup.

## Local acceptance

Standard `Pkg.test` with `--load-orders` passes 6,390 assertions across 71
top-level groups on Julia 1.13.1 with four threads and Julia 1.10.10 with one
thread. The minimum-version run resolves an independent environment against the
actual checkout. Every ordered testset name and assertion count matches across
versions; all eight fresh-process loading scenarios pass (92.8/76.9 seconds).
Source, tests, and root Project/Manifest hashes remain unchanged during each run.

The 811 added assertions cover short-observable promotion, complex and wider
domain seeds, underflow recovery, empty batches, zero-qubit registers, snapshot
ownership, repeated and concurrent pullbacks, nested/shared multi-parameter
gates, and arithmetic-domain changes across fixed-channel checkpoints.

Independent standard fixture tests pass on both versions: `MOSSDemoBackend`
9, `MOSSDemoGates` 185, and `MOSSDemoDifferentiation` 235 assertions each.
Fourteen fresh benchmark compatibility processes pass, seven per version:
scalar core/AD 16/20 warmed rows, pure-batch core/AD 18/21, new batch core/AD
52/60, and new core first-call 26. These 426 smoke rows check the scripts and
AD boundaries; they are separate from the 884 formal measurement records.

The [validation record](cpu-batch-2026-10-20/validation.json) retains commands,
versions, per-testset counts, compatibility results, and source/environment
proofs. Independent review replays the three-file patch against the baseline
and verifies all source hashes, paired controls, comparison arithmetic, and
artifact checksums. CI includes small core/optional-AD batch harness checks on
both supported versions; these results describe local acceptance.
